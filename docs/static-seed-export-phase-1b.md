# Static seed export — Phase 1b

This document explains the static seed export layer added on top of the
Phase 1 schema plan (`docs/database-schema-phase-1.md`,
`docs/database-seed-map.md`). It generates normalized JSON seed files from
the current TypeScript content modules — a mechanical, deterministic
snapshot of today's data in the shape the future database schema expects.

**Nothing here connects the site to a database.** No driver, ORM, or CMS
dependency was added. The generated files are plain JSON on disk, produced
by a standalone script that is never imported by `app/`, `components/`, or
`lib/`.

grows; the manifest never will).

## How to regenerate seed files

```bash
npm run seed:export
```

Runs `node scripts/export-phase-1-seed.mjs`, which:

1. Registers a `require()` hook (`scripts/seed-lib.mjs`) that transpiles
   `.ts` files on the fly using the `typescript` package's
   `ts.transpileModule` API — **`typescript` is already a devDependency of
   this project** (used for `next build`'s type-checking step), so this adds
   no new dependency. The hook also resolves the `@/...` path alias used
   throughout `lib/`, the same alias Next.js resolves via `tsconfig.json`.
2. `require()`s the actual source modules directly — `lib/products/catalog.ts`,
   `lib/products/details.ts`, `lib/services.ts`, `lib/content.ts`,
   `lib/partnerProjects.ts`, `lib/assets.ts` — so the seed data is read from
   the single real source of truth, never hand-copied or re-typed.
3. Reshapes that data into the normalized rows described in
   `docs/database-schema-phase-1.md`, assigns deterministic IDs (see below),
   and writes each table to its own JSON file under `data/seed/phase-1/`.

Re-running the script is safe and idempotent: every ID is derived
deterministically from a slug/key already in the source data (never a random
UUID), so re-running produces byte-identical output as long as the source
`lib/*.ts` files haven't changed. This was verified directly: running the
script twice in a row and diffing the output produces zero differences.

## How to validate seed files

```bash
npm run seed:validate
```

Runs `node scripts/validate-phase-1-seed.mjs` (pure Node.js, no dependencies
at all — it only reads the already-generated JSON, it never touches the TS
source). It checks:

- No duplicate `id` within any single file.
- No duplicate `slug` (or `key`, for media assets) where slugs are meant to
  be unique (`product_categories`, `products`, `services`, `partners`,
  `partner_projects`, `media_assets`).
- Every `products[].category_id` resolves to a real `product_categories` row.
- Every `products[].image_asset_id` (when not null) resolves to a real
  `media_assets` row.
- Every `product_details[].product_id` resolves to a real `products` row.
- Every `product_options[].product_id` resolves to a real `products` row.
- Every `service_sections[].service_id` resolves to a real `services` row.
- Every `partner_projects[].partner_id` resolves to a real `partners` row.
- Every `partners[].asset_id` (when not null) resolves to a real
  `media_assets` row.
- Every `partner_project_products[].partner_project_id` resolves to a real
  `partner_projects` row, and `product_id` (when not null) resolves to a
  real `products` row.
- Every localized field (recursively, across all files) carries **both**
  `en` and `ar` keys — an object with only one of the two is flagged as a
  structural error. A `null` *value* for a key that's present (e.g.
  `media_assets[].alt_localized.ar`, which is intentionally `null` today —
  see warnings below) is **not** an error; only a genuinely missing key is.

The validator exits non-zero and lists every problem if any check fails —
this was exercised directly (a temporary duplicate ID and a dangling foreign
key were introduced, confirmed the validator caught both and correctly
cascaded the failure to every dependent row, then the test change was
reverted before this was documented).

## What is intentionally not included

- **No `image`/media files.** `media_assets.json` references paths as
  strings (e.g. `/assets/products/arabic-bread.webp`); the actual image
  files still live only in `public/assets/...`. `lib/assets.ts` remains the
  runtime source of truth for the live site.
- **No database connection, migration runner, ORM, or CMS.** This is a
  seed-export layer only, not a schema-migration tool. Running these scripts
  never touches any database.
- **`form_enquiries` has no seed file.** It's documented separately in
  `docs/database-schema-phase-1.md` because it has no source data to export
  at all today — the contact form only opens a `wa.me` link client-side and
  persists nothing.
- **Arabic alt text for media assets.** `lib/assets.ts`'s `altTexts` map is
  English-only today; every `media_assets[].alt_localized.ar` is `null`
  (not a guessed/duplicated value) and flagged in `seed-manifest.json`'s
  `warnings`. Authoring real Arabic alt text is a content task, not a script
  task.
- **`partner_project_products.json`'s richer fields.** The task that
  requested this export specified exactly 5 fields for this file (`id`,
  `partner_project_id`, `product_id`, `product_name_localized`,
  `sort_order`). `lib/partnerProjects.ts`'s source data has more
  (`category`, `shortDescription`, `keyNotes`, `nutritionHighlights`,
  `image`, `status`, including `NEEDS_VERIFICATION` placeholders) — these
  are available for a future, richer migration (see
  `docs/database-seed-map.md`) but weren't exported here to match the
  requested field list exactly.
- **A 4th "Al Taj" partner row.** `lib/assets.ts` reserves a `partners.alTaj`
  asset key for a possible future partner, but `lib/content.ts`'s
  `manufacturingPartners` has no corresponding entry — no partner row was
  invented for it; this is flagged in `seed-manifest.json`'s warnings
  instead.

## Seed IDs

All IDs are stable strings derived from an existing slug or asset-manifest
key — never random UUIDs — per this task's explicit requirement:

| Entity | Pattern | Example |
|---|---|---|
| Product category | `cat_<slug>` | `cat_flatbread_wraps` |
| Product | `prod_<slug>` | `prod_arabic_bread` |
| Product detail | `detail_<slug>` | `detail_arabic_bread` |
| Product option | `opt_<slug>_<type>_<index>` | `opt_arabic_bread_use_case_0` |
| Service | `svc_<slug>` | `svc_distribution` |
| Service section | `svcsec_<slug>_<section_type>` | `svcsec_distribution_coverage` |
| Partner | `partner_<slug>` | `partner_ektifa` |
| Partner project | `proj_<slug>` | `proj_halsa_bake` |
| Partner project product | `ppp_<project_slug>_<product_slug>` | `ppp_ektifa_burger_buns` |
| Media asset | `media_<singular_section>_<key_as_snake_case>` | `media_product_arabic_bread` |

Partner project products are scoped by *both* the project slug and the
product slug (not just the product slug) because several partner projects
reuse the same product slug — e.g. `burger-buns`, `maamoul`, and `tamriya`
each appear under more than one partner project in the source data. Using
only the product slug would have produced duplicate IDs.

## How this will be used later by a real database migration

Once an actual PostgreSQL database exists (per
`docs/database-schema-phase-1.md`'s recommendation), these JSON files become
the direct input to a `COPY`/bulk-insert seed step — each file maps 1:1 to
one of that document's tables, in the field names and shapes already
specified there. A future migration tool (whether raw SQL, Prisma, Drizzle,
or something else — none of which are decided or installed yet) would:

1. Run the schema migration (create the tables).
2. Read these JSON files and insert them, table by table, in the dependency
   order already documented in `docs/database-seed-map.md` (categories →
   products → details/options → services → sections → partners → projects →
   project products → media assets).
3. Resolve the few "soft" references that are currently string-keyed instead
   of DB-keyed (there are none left to resolve here, actually — this export
   already resolved `image_asset_id`/`asset_id` against `media_assets.json`
   and `product_id` against `products.json` at export time, using the IDs
   above; a real migration just inserts the IDs as literal primary keys).

This export exists specifically so that step is a straightforward bulk
insert, not a redesign — the normalization decisions (JSONB localized
fields, which arrays became child tables vs. JSON columns, etc.) are already
made and already reflected in these files.

## Why this still does not change runtime behavior

- Nothing under `app/`, `components/`, or `lib/` imports anything from
  `data/seed/phase-1/`, `scripts/export-phase-1-seed.mjs`,
  `scripts/validate-phase-1-seed.mjs`, or `scripts/seed-lib.mjs`. Confirmed
  by grepping the codebase before finishing this task.
- `next.config.mjs`'s `output: "export"` is untouched. `npm run build`
  produces the exact same set of static routes as before this task.
- The two new `npm run seed:*` scripts are standalone Node.js invocations —
  they are not part of `npm run build`, `npm run dev`, or `npm run lint`,
  and don't run automatically at any point in the site's build or deploy
  process.
- No entry in `package.json`'s `dependencies` or `devDependencies` changed —
  `typescript` was already installed for `next build`'s own type-checking;
  these scripts merely reuse it via its public API.
